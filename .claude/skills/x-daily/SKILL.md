# X日次投稿

## このスキルの目的

@sns_hannou_ma（SNS反応まっぷ）の今日のX投稿を準備する。
実際の投稿操作はユーザーが行う。ここでは「何を・どこに・どう投稿するか」を決めて文面と画像を出す。

**日付の扱い:** 指示文に日付が書かれていても、記録に使うのは**実際の日付**。
食い違っていたら書き込む前に確認する。指示の日付をそのまま記録すると1日ずれたまま気づけない
（`refresh` の `--date` で同じ事故があった）。

**前提: ログイン済みChromeが要る。** X検索も自分の投稿の表示回数も、ログアウト状態では取得できない
（2026-08-10 検証。検索はログイン画面へリダイレクトされ、自分の返信は数字ごと隠れる）。
ログインが切れていたら、無理に進めずその旨を伝えて止まること。

## 毎日の作業手順

### ① 枠の確認

x-posts.md の直近1週間の実績を確認して以下を把握する：

- 今週のURLなしリプライ: 何本済みか（**本数目標は無い。候補があるだけ打つ**。2026-08-10 に「毎日2〜3本」を廃止）
- 今週のURL付き流入投稿: 何本済みか（上限: 週1〜2本）
- 直近2日でリプライしたアカウント（同じアカウントへの連日リプライは避ける）

### ② X検索で今日の素材を探す（Yahooリアルタイム検索は使わない）

**2026-08-10 変更。** Yahooリアルタイム検索では**返信数と経過時間で絞り込めない**ため、
新基準（返信が少ない・投稿が新しい）に合う候補を選べなかった。
X本体の「最新」タブなら条件を検索式に直接書ける。**こちらを使う。**

ログイン済みChromeで次のURLを開く（`f=live` が「最新」タブ）。

**本命クエリ（まずこれ）:**

```
https://x.com/search?f=live&q=(消費税減税 OR 皇室典範 OR 副首都 OR 部活動 OR 生成AI 著作権 OR 自転車 青切符 OR 高齢者 免許 OR 辺野古 OR あだ名禁止) -filter:replies -filter:retweets min_faves:80
```

**速報を拾うクエリ（大きなニュースが出た日）:**

上と同じで `min_faves:80` を **`min_faves:10`** に下げる。より新しい投稿が出る。

検索式の意味:

| 部分 | 効果 |
|---|---|
| `f=live` | 「最新」タブ。新しい順に並ぶ＝**返信がまだ少ない投稿が上に来る** |
| `-filter:replies` | 他人への返信を除外（元投稿だけにする） |
| `-filter:retweets` | リポストを除外 |
| `min_faves:N` | いいね数の下限。元投稿の規模を調整する |

**2026-08-10 の実測（同じ時刻に両方を実行して比較）:**

| 条件 | 経過 | 返信数 | 元投稿の表示 |
|---|---|---|---|
| `min_faves:10` | 18〜60分 | 0〜4件 | 250〜2,000 |
| `min_faves:80` | 1〜3時間 | 3〜12件 | 3,000〜**11,000** |

`min_faves:80` の結果は、最高成績だった @bunshun_online（11,070表示・返信4件・3時間15分 →
到達率5.80%）とほぼ同じ形。**まずこちらを既定にする。**

**候補の絞り込み（検索結果ページで実行する）:**

各投稿を開かなくても、検索結果から返信数・経過時間・表示回数をまとめて読める。
Chrome MCP の javascript_tool で以下を実行する。

```js
const now=Date.now();
JSON.stringify([...document.querySelectorAll('article[data-testid="tweet"]')].slice(0,12).map(a=>{
  const g=a.querySelector('[role="group"]');const aria=g?g.getAttribute('aria-label')||'':'';
  const t=a.querySelector('time');const dt=t?t.getAttribute('datetime'):null;
  const num=re=>{const m=aria.match(re);return m?+m[1]:0;};
  const h=[...a.querySelectorAll('a[href*="/status/"]')].map(x=>x.getAttribute('href')).find(x=>/\/status\/\d+$/.test(x));
  return {分:dt?Math.round((now-new Date(dt))/60000):null, 返信:num(/(\d+)\s*件の返信/),
          表示:num(/(\d+)\s*件の表示/), url:h,
          txt:((a.querySelector('[data-testid="tweetText"]')||{}).innerText||'').replace(/\n/g,' ').slice(0,40)};
}),null,1)
```

**注意:** `javascript_tool` では `(async()=>{...})()` の戻り値が空になる。
上のように**トップレベルの式**として書き、`JSON.stringify` で返すこと。
結果が空なら描画待ちなので、少し置いてもう一度実行する。

出てきた候補から **返信が少なく・経過が短い**ものを選ぶ。表示回数は参考。
同じアカウントへの連日リプライは避ける（①で確認した直近2日のリストと突き合わせる）。

**良いポストの基準（2026-08-10 夜に再検証して訂正）:**

**同日の昼に「返信50件未満・4時間以内」を優先条件としたが、14本で検定したところ予測力がほぼ無かった。**
以下が検定結果（該当群と非該当群の自リプライ表示）。

|---|---|---|
| 返信50未満 かつ 4時間以内 | 92 (n=4) | 55 (n=10) |

分布そのものが偏っている（全14本: 中央値55 / 平均142 / 標準偏差187、平均が中央値の2.6倍）。
**少数の大当たりが全体を作る形で、事前に当たりを見分ける手立ては見つかっていない。**
上位3本で全体の70%、下位10本を合わせても7%しかない。

### したがって、選定は「絞り込み」ではなく「明らかな地雷を避ける」に留める

1. **避けるのは、元投稿の返信数が極端に多いもの**（目安100件超）。
   唯一はっきり沈んだのは @tamakiyuichiro の**返信534件で15表示**（到達率0.007%）
2. **それ以外は絞り込まない。** 経過時間・元投稿views・いいね数はいずれも予測力が確認できていない。
   参考として記録はするが、**見送る理由に使わない**
3. **候補があるだけ打つ。上限を設けない**（同一アカウントへの連日リプライ回避は維持）

**当たりを事前に選べない以上、試行回数が唯一効く手段。** 旧版にあった
「返信数と経過時間で絞る」「4時間以内」は削除した。**復活させるならデータで示すこと。**

### 未検証のリスク（増やすときに見ておく）

**本数を増やしたときにXが抑制するかは分かっていない。** 実測できた日はすべて4本で比較対象が無い。
増量する週は、1本あたりの中央値が落ちないかを必ず確認すること。落ちたら本数を戻す。

- 速報系メディア（初動の速さ重視）と個人論客（リプライが目立つ）を使い分ける
- 返信数は投稿前に確認する。②のX検索を使えば検索結果の一覧からまとめて読める

### ③ リプライ文を生成する（毎日メイン作業）

見つけたポストに対してURLなしのリプライ文を作成する。**本数の上限は設けない**（候補があるだけ）。

**リプライの型:**
- 論点整理型: 「賛成側はXを、反対側はYを重視している構図だと思います」
- 視点追加型: 「AとBは別々に考えた方が整理しやすい論点かもしれません」
- 問いかけ型: 「制度の是非より、運用体制の話に見えるのですが、どうでしょうか」
- エッジ型: 少し踏み込んだ表現で、「〜ってあるんでしょうか」「〜かもしれない」で締める（当たり障りなすぎない文面）

**画像ルール:**
- リプライには**必ずインフォグラフィック画像を添付**する（hero画像よりインフォグラフィック優先）
- docs/images/ の `*-infographic-wide-*.webp` から内容に最も合うものを選ぶ
- 事故・遺族案件など感情的なテーマは画像なし（不適切になるリスク）

**禁止事項:**
- URL含める（URLなしリプライが基本）
- 自サービスの宣伝文句（「詳しくはこちら」など）
- 強い賛否を表明する（中立・論点整理スタンスを保つ）
- 同じアカウントへの連日リプライ
- 「SNSでは○%が賛成」「意見が真っ二つ」「意外な結果に」等の煽り表現（`X_POSTING_GUIDE.md` §2 参照）

### ④ 流入投稿（週1〜2本、URL付き）

URL付き枠が残っている場合のみ。**書き方は `X_POSTING_GUIDE.md` に従う。**

**4つの型（X_POSTING_GUIDEより）:**
- 型A: 問いを立てる（基本形）
- 型B: 前提の食い違いを見せる（最も強い型。サイトにしか書けない）
- 型C: 反対側の最も強い理由を出す（`arguments` の `strongest` を使う）
- 型D: 分かっていないことを開示する（`unresolved` を使う）

**必須ルール:**
- URLには必ずUTMを付ける: `?utm_source=x&utm_medium=social&utm_campaign=post_YYYYMMDD`
- 「SNSでは○%が賛成」「意外な結果に」「意見が真っ二つ」は使わない
- 判定基準: 読んだ人が「**自分はどう考えるだろう**」と思うか。「へえ」で終わる文はクリックされない
- GSC上位テーマ（高齢者免許・AI著作権・部活・自転車青切符）と `arguments` 実装済みテーマを優先
- 週2本が上限（それ以上は宣伝アカウントと見なされリーチが落ちる）

### ⑤ 論点ポスト（週2〜3本）

プロフィールに「考察アカウント」としての蓄積を作るためのポスト。
リプライは他人のスレッドに流れるが、このポストは自分のプロフィールに残る。

**2026-08-10 に「毎日1本・必須」から「週2〜3本」へ緩めた。**
実測では単独ポストの到達がリプライの約10分の1しかない（論点ポスト6・6、通常ポスト10、
流入投稿17 に対し、リプライは中央値59・最大642）。
ただし**この枠の目的は到達ではなくプロフィールの中身**なので、到達が低いことを理由に廃止はしない。
**目的が果たされているかは未検証。** フォロワー数とプロフィールアクセスを記録して4週間後に判断する
（フォロワー数は初回スナップショット以外すべて null で、一度も継続取得できていない）。

**URL付き流入投稿への昇格:** 論点ポストにURLを付けて④の流入投稿を兼ねることも可能。
その場合は④のルール（UTM必須・型A〜D・煽り禁止・週2枠消費）が適用される。
URLなしの場合はスパムリスクゼロのまま。

**ポストの作り方:**

その日の②のX検索で見つけた話題をもとに、以下のパターンから選んで作る。

**パターンA: 問いかけ型（最優先・RT/引用されやすい）**
最後を「？」で閉じる。読んだ人が「確かに」「自分はこう思う」と反応したくなる問いを投げる。
例:「○○について、「制度として正しいか」と「実際に機能するか」は別の問題なのに、同じ議論の中でごっちゃになりやすい。これ、どちらの話をしているか意識するだけで議論が変わりませんか？ #SNS反応まっぷ」

**パターンB: 構図整理型（二極化トピック向き）**
「同じ根拠から逆の結論」「賛成も反対も同じ○○を根拠にしている」など対立構図を可視化する。
例:「○○の議論、賛成派も反対派も「防災」を根拠にしている。機能分散でリスク減vs共倒れリスク。同じ根拠から正反対の結論が出る、唯一の激戦論点。 #SNS反応まっぷ #ハッシュタグ」

**パターンC: データ引用型（SNS反応まっぷの分析結果を使う）**
世論調査やサイトの分類結果の数字を使う。数字の「矛盾」「意外性」を切り口にする。
例:「皇室典範改正、女性天皇容認81%なのに今回の改正反対54%。同じ人が両方に入っている可能性があって、「賛成だがこのやり方は違う」層が多数派かもしれない。 #皇室典範 #SNS反応まっぷ」

**パターンD: エッジ型（断定を避けつつ踏み込む）**
「〜ってあるんでしょうか」「〜は本当に〜なのか」で締める。当たり障りなさすぎない文面。
例:「副首都法案、法案の本体が空欄のまま通った。枠組みだけ先に作る手法、うまくいった事例ってあるんでしょうか。 #副首都法案 #SNS反応まっぷ」

**制約:**
- 140文字以内
- 原則URLなし（スパムリスクゼロ）。④の流入投稿を兼ねる場合のみ、UTM付きURLを許可する
- ハッシュタグ1〜2個（#SNS反応まっぷ 必須＋テーマ別1個）
- 強い賛否を表明しない（中立・論点整理スタンスを保つ）
- 毎日違うテーマで書く（同じテーマの連日投稿は避ける）
- **必ずインフォグラフィック画像を添付する**（テーマの論点図解）
- **問いかけ型（パターンA）を最優先で使う**（RT/引用されやすい）
- 「SNSでは○%が賛成」「意見が真っ二つ」「意外な結果に」「あなたはどっち？」は使わない（`X_POSTING_GUIDE.md` §2）
- 数字を使う場合は「矛盾」「食い違い」の切り口で使う（単なる割合の紹介にしない）

## 作業完了後

投稿案をユーザーに提示したら、実施後に以下を順番に行う。

### 1. x-posts.md に追記する

表の形式は **`元投稿views ｜ 自リプライ表示 ｜ 元投稿の返信数 ｜ 元投稿からの経過`** に揃える。
**この見出しを勝手に変えないこと。** 2026-08-06 に列名を変えたとき、管理画面の集計が
黙って空扱いになり、5日ぶんの実測値が消えていた。現在は未知の列があると
`build_admin_dashboard.py` がエラーで止まる（`scripts/admin_dashboard/collect.py`）。
列を増やす必要が出たら、collect.py と tests/test_admin_dashboard.py も同時に直す。

投稿直後は `自リプライ表示` に **`未計測（投稿直後）`** と書く。数値を入れない。

### 2. 自リプライ表示を本計測する（投稿の24〜48時間後）

**投稿直後の値は判断材料にならない。** 8/8の実測では 4→51（12.8倍）、2→37（18.5倍）に伸びた。
前日以前の「未計測」行が残っていたら、この作業で埋める。

取得方法（X Premium は不要。表示回数はポストの個別ページに公開表示される）:

1. ログイン済みChromeで `https://x.com/sns_hannou_ma/with_replies` を開く
2. 各ポストの `[role="group"]` の `aria-label` から表示回数を読む
3. 一覧が古い投稿まで遡れない場合は、投稿URLを直接開いて同じ要素を読む

**個別ポストページで「返信先」が表示されなくても、単独ポストと判断しないこと。**
親投稿の描画に失敗することがある（2026-08-10 に誤判定した）。リプライか単独かは
`with_replies` タブか、記録済みの `返信先:` 行で確認する。

記録するときは **計測日時または投稿後の経過時間を必ず併記**する（例: `**642**（8/10 昼計測・約3時間後）`）。
まだ伸びている途中の値なら、その旨も書く。

未計測投稿の抽出と書き戻しには `scripts/x_post_views.py` を使う。投稿候補探しとは
別工程なので、この計測中にX検索や投稿案作成へ進まない。

```bash
# ① 何をするか: 投稿から24時間以上たった未計測投稿を一覧する
python3 scripts/x_post_views.py pending --json
# 成功の形: 対象がJSONで表示される。対象がなければ []

# ② 何をするか: Chromeで取得した表示回数を未計測箇所だけに記録する
python3 scripts/x_post_views.py apply \
  --view <投稿ID>=<表示回数>,<いいね>,<リポスト> \
  --measured-at <YYYY-MM-DDTHH:MM:SS+09:00>
# 成功の形: 「1件を記録しました」と表示される。既存数値ならエラーで止まる

# ③ 何をするか: 自分の投稿に付いた返信を一覧する（ログイン不要）
python3 scripts/x_post_views.py replies
# 成功の形: 返信が付いた投稿のURLが並ぶ。無ければ「返信が付いた自投稿はありません。」
```

**いいね・リポストは表示回数と同じ `aria-label` から一緒に読める**ので、計測のたびに入れておく
（例: `"6 件のいいね、1 件のブックマーク、642 件の表示"` → `--view <ID>=642,6,0`）。
省略もできるが、**後から時間帯・型ごとに分析するとき、記録していない項目は復元できない**。
列は増やさず注記に入る形にしてある（実績表の既存行はすべて8列で、列を足すと行ごとにずれるため）。

### 自分のリプライに返信が付いたとき

`replies` は**返信が付いた自投稿を一覧するだけ**。返すかどうかは毎回判断する。
検知はログイン不要の公開APIで行うので安く回せる。

**必ず返す必要はない。** 相手が荒れている場合は見送る。返す場合は通常のリプライと同じ方針で、
**相手の人物評価には乗らず、検証可能な論点に戻す**（2026-08-09 の @FPXLej8w7O61326 への
会話フォローが実例。「積極財政論者は市場評価を気にしない」という人物評価には乗らず、
どの指標がどの水準なら危険信号かという話に戻した）。

記録先は `### 会話フォロー YYYY-MM-DD` 節。会話の続きなので画像は再添付しない。

**効果は期待しすぎないこと。** 会話フォローの実測は1本のみで8表示。
リプライ本体の中央値59と比べて低い。ただし検知も記録もほぼ自動なのでコストもほぼゼロ。

`pending` の `timing` は、24〜48時間なら `due`、48時間超なら取りこぼしを示す
`overdue`。24時間未満の `waiting` は通常表示されず、`--all` のときだけ出る。
Chromeでは各URLを直接開き、URLの投稿IDと一致する自投稿の記事内の
`[role="group"]` を読む。ページには親投稿の同じ要素もあるため、ページ全体の最初の
`[role="group"]` を使わない。

**ログインなしで取れるもの／取れないもの（2026-08-10 検証）:**

公開APIで投稿の情報が取れる。ログイン不要。

```
curl -s "https://cdn.syndication.twimg.com/tweet-result?id=<投稿ID>&token=a"
```

| 項目 | 取得可否 | 備考 |
|---|---|---|
| 返信数（`conversation_count`） | ○ | 候補選定の第1条件に使える |
| いいね（`favorite_count`） | ○ | |
| 投稿時刻（`created_at`） | ○ | 経過時間の算出に使える |
| 添付画像（`photos[].url`） | ○ | **画像有無の判定はこれを使う** |
| **表示回数** | **×** | フィールド自体が存在しない |

**表示回数だけはログイン済みブラウザが要る。** これが計測を自動化しにくい理由。

画像の有無を `[data-testid="tweetPhoto"]` で判定すると誤ることがある
（2026-08-10 に添付済みの投稿を「画像なし」と誤判定した）。上のAPIで確認すること。

### 3. THEMES.yaml の x_posted_at を更新する

その日にリプライ・論点ポストで触れたテーマの `x_posted_at` を今日の日付に更新する。
テーマ名とキー名の対応例：

| テーマ | THEMES.yaml のキー |
|--------|-------------------|
| 副首都法案 | fukushuto |
| 皇室典範改正 | koshitsu-tenpakai |
| 憲法改正 | constitutional-amendment |
| 生成AI・著作権 | ai-copyright |
| 高齢者免許 | elderly-license-revocation |
| 部活地域移行 | bukatsu-chiiki |
| 自転車青切符 | bike-blue-ticket |
| あだ名禁止 | school-nickname |

更新方法: 該当テーマの `x_posted_at: YYYY-MM-DD` を今日の日付に書き換える。
（🔥注目バッジが2日間表示される）

### 4. トップページを同期・検査する

`THEMES.yaml` の更新をトップページの `var B` に反映し、台帳との一致を確認する。

```
python3 scripts/sync_portal_stats.py
python3 scripts/verify_top_page.py
```

検査が失敗した場合はコミットせず、原因を修正して再実行する。
