# 本番反映（マージ → push → 公開確認 → 片付け）

## この作業は何か

作業ツリー（作業用のコピー）で仕上げたものを、main に取り込み、GitHub Pages で
公開されている本番サイトへ届けるまで。**ページを直す作業そのものは対象外**で、
そちらは `OPERATIONS.md` と `DATA_REFRESH.md` を見ること。

短い工程だが、ここで失敗すると「手元では直っているのに公開版が古い」「マージ後に
検査が落ちる」という、あとから気づきにくい壊れ方をする。

## 最初に読む2行

- **オーナーにコマンドを渡さない。マージも push もAIが実行する。**
  `-m` を付けない `git merge` はエディタ（vim）を開き、オーナーは抜け方が分からず止まる。
  2026-08-17 とそれ以前に実際に起きた。
- **検査は「マージした後の main」で通す。** 作業ツリーで通したかどうかは根拠にならない。

## 手順

### ① 作業ツリーがコミット済みか確認する

```sh
cd <作業ツリー> && git status --short
```

成功の形: 何も出ない。出たら、その差分を先にコミットする。**`data/verification/` の
未追跡ディレクトリが `??` で出たら必ずコミットする**（収集の履歴を本文なしで残す唯一の場所。
作業ツリーを消すと失われる）。

### ② 作業ツリーにしか無い非公開データを共有ツリーへ移す

`social-samples/` の一部は gitignore 対象で、**git では運ばれない**。移し忘れると
マージ後に検査が「ファイルがない」で落ちる。

```sh
cd <作業ツリー> && rsync -an --itemize-changes social-samples/ <共有ツリー>/social-samples/ | grep -v '^\.'
```

成功の形: 何も出ないか、`>f..t....`（中身は同じで日時だけ違う）だけ。
`>f+++++++` のように**新規ファイルが出たら、`-an` を外して実際にコピーする**。

テーマによって、正典が git 管理のものと gitignore のものがある。**どちらかを覚えて
判断しない。毎回この差分で確かめる。**

### ③ マージする（AIが実行する）

```sh
cd <共有ツリー> && git merge --no-ff task/<ブランチ名> -m "Merge branch 'task/<ブランチ名>'"
```

**`-m` を省かない。** 省くとエディタが開く。
成功の形: `Merge made by the 'ort' strategy.` と変更ファイル一覧が出る。

衝突したら、その場で直さずオーナーへ報告する（別セッションが同じ場所を触っている
可能性がある）。中止は `git merge --abort`。

### ④ マージ後の main で検査を通す

```sh
cd <共有ツリー>
python3 scripts/verify_theme_page.py
python3 scripts/verify_number_provenance.py
python3 scripts/verify_top_page.py
python3 -m unittest discover -s tests
```

成功の形: それぞれ `NG 0件` / 終了コード0 / `OK`。

**ここで初めて分かることがある。** 作業ツリーの分岐元が古いと、そこでは落ちていた
テストが main では通る（逆もある）。2026-08-17、作業ツリーで1件失敗していた
X投稿のテストは、分岐元が古いだけで main では通っていた。
**作業ツリーで見た結果をそのまま報告しない。**

落ちたら push しない。直して作業ツリー側でコミットし直し、②から。

### ⑤ push する（AIが実行する）

```sh
git log --oneline origin/main..HEAD | cat
git push
```

1行目で、これから送る内容を確かめてから送る。
成功の形: `0811403..d41564e  main -> main` のような行が出る。

### ⑥ 公開サイトで実物を確認する

GitHub Pages は反映に1〜数分かかる。**push した直後に見ると古い版が返る。**
待つときは `until` で条件が満たされるまで回す（短い `sleep` を並べない）。

```sh
until curl -s "https://issue-stance-lab.github.io/sns-reaction-map/<テーマ>-reaction-map.html" \
  | grep -q "<今回変えた文字列>"; do sleep 15; done; echo "公開反映を確認"
```

`<今回変えた文字列>` は、今回の更新でしか現れない文字列を選ぶ（件数など）。
成功の形: `公開反映を確認` が出る。5分待って出なければオーナーへ報告する。

**トップページも見る。** テーマページだけ直してトップの件数が古いままだと、
同じサイトの2か所で違う数字が出る。

### ⑦ 片付ける

```sh
cd <共有ツリー> && python3 scripts/backup_private_data.py --dest /Volumes/HD-LE-B/issue-stance-private-backups
git worktree remove <作業ツリー>
```

バックアップは**マージ後の main の上で取り直す**（`THEMES.yaml` と `.gitignore` を見て
対象を決めるため、古いブランチで取ると新しい正典が漏れる）。
成功の形: `復元確認: OK` が出る。

`git worktree remove` が「未追跡ファイルがある」で断られたら、**消す前に②をやり直す**。
そのツリーにしか無い非公開ファイルが残っている合図。

### ⑧ 台帳を更新する

公開まで行った更新なら、`THEMES.yaml` の `updated_at` / `collect_at` / `refresh_at` /
`collect_delta` が今回の値になっているか確かめる（本来は反映前に済んでいるはず。
ここは最後の網）。テーマ横断の課題が片付いたなら `TASK_BOARD.md` も直す。

## やらないこと

- **`gh pr merge` を使わない。** 権限で弾かれる。マージはローカルの `git merge` で行う
- **`git checkout -- <ディレクトリ>` を使わない。** 他セッションの未コミット変更を消す。
  戻すときは自分が変えたファイルだけをパス指定する
- **共有ツリーで `git checkout -b` や `stash -u` をしない。** 別セッションのファイルが消える
