# note 運用

## このスキルの目的

SNS反応まっぷのWebsiteへの理解ある流入を作り、note単体でも読者が論点を理解できる記事にする。
被リンクや収益は結果として測定するが、編集の結論や扱う声を変える理由にはしない。

**宣伝記事は書かない。** 「〇〇件のデータから分析した」という記事を書き、
その記事の中でテーマページを自然にリンクする。読者の理解を深めることが目的。

## noteは意見を書く媒体（最重要）

**サイト（SNS反応まっぷ）は中立を規定している。noteはそうしない。**
サイトと同じ中立の要約をnoteに長く書いても、読者には「で、何が言いたいの？」しか残らない。
サイトが「どんな意見があるか」を並べる場所で、noteは「その並びを読んで編集部が何を考えたか」を書く場所。

### 守ること

- **記事に主張を1つ置く。** 記事全体が支える結論を1文で書けないなら、まだ書き始めない
- **主張は本文の地の文で書く。** 「［編集部の読み］」のような箱に意見を隔離しない。
  箱に入れた瞬間、本文は中立の説明に戻り、記事は退屈になる
- **主張はリードに置く。** 結論を最後まで伏せない
- **一人称は「編集部」。** 初出で「SNS反応まっぷ編集部」と名乗る。
  「私たち」「自分たち」だけで主張すると、読者に「それは誰か」が伝わらない
- 記事末の注記に **「記事中の評価と主張は編集部のものです」** を必ず入れる

### 構成は「議論の順」で書く（作業の順で書かない）

やってはいけないのは、**調べた手順のまま書くこと**（集めた→分類した→読み直した→資料に当たった）。
これは書き手の作業記録であって、読者が知りたい順ではない。

正しい順は4つ。

1. **主張** — 場面か具体物から入り、結論を先に言う（数字から始めない）
2. **反論** — 自分の主張に不利な事実を、自分で先に出す
   （見出しは「自分たちに不利な数字から出します」のような書き手側の宣言にせず、
   「227件のうち136件は賛成だった」のように、その節で出す事実そのものを書く）
3. **根拠** — 反論を越える材料を出す。数字と引用はここで使う
4. **結論** — 主張を言い直し、何が変われば違う結果になるかを書く

### 主張してよい範囲

- 制度・仕組み・報道の読み方への評価は書いてよい（例:「この改革は負担の答えになっていない」）
- 特定の政党・個人・企業への支持や攻撃は書かない
- 投稿者個人を評価しない。批評の対象は制度と数字の扱い方に限る
- 主張と事実は文単位で分ける。推測には「〜と考えます」を付け、根拠の範囲を書く
  （全件読んだのか、例からの読み取りなのかを明示する）

## 数字の扱い（2026-08-28 追加）

SNSの集計を扱う以上、記事に件数は必ず出る。**出し方を間違えると、記事は数字の羅列になる。**
2026-08-28、note第2回でオーナーから「件数ばかり列挙してつまらない」「読み進めようと思えない」と
指摘された。原因は文章力ではなく、**記事の背骨が件数になっていたこと**だった。

### 守ること

- **件数を文の主語にしない。** 「30件が言っていたのは」ではなく、その30件が何を言ったかを書く。
  主語は人か仕組みにする
- **本文に置く数字は4種類まで。** 残りは図と記事末の注記に預ける。
  読者は内訳を知りたければ図を見る。本文で全部並べると、読み進める人が止まる
- **区分の一覧を本文で列挙しない。** 多かった2つを声として書き、内訳は図が担う。
  図に件数が入っていることを、貼り付け手順に明記する
- **「この記事で分かること」は、単体で読める文にする。** 件数を並べない。
  「136件が、何に賛成しているのか」は、前の文を読んでいないと意味が通らない
- **専門用語は初出で言い換える。** 給特法、兼職兼業、論点別。カッコか直後の一文で短く

### 検査

`scripts/verify_ai_tone.py` が、貼り付け用の本文（`*-FINAL.md` / `*-CANDIDATE.md`）に
「◯件」が8回を超えて出ていたら落とす。記事末の注記は数えない。
上限は `configs/ai-tone.json` の `note_counts`。

## 記事の型

### 型A：テーマ別分析（主力）

テーマひとつを深掘りする。検索流入は狙うが、二択や割合の刺激ではなく、論点と背景が分かるタイトルにする。

**構成：**

1. **タイトル**（例）
   - 「AI著作権問題、SNS投稿600件を分析したら3つの論点に集約された」
   - 「高齢者免許返納、SNSの賛否を1000件分けてみた」
   - 「消費税減税に反対する人は何を懸念しているか——SNS投稿を分類した」

2. **リード（100字以内）**
   「〇〇についてのSNS公開投稿〇件を収集し、賛成・反対・論点別に分類しました。」

3. **主な論点（3〜5個）**
   各論点の件数・背景・代表的な主張をまとめる。数字は出所と対象範囲を併記する。

4. **スタンスマップの画像**
   `docs/<theme>-reaction-map.html` のスクリーンショットを貼る。
   画像の意味を本文でも説明し、画像だけに重要な情報を預けない。

5. **CTA（必須）**
   「論点の詳細・全分布・投票はこちら」として、テーマページへの UTM 付きリンクを貼る。

6. **注記**
   「データ元：Yahoo!リアルタイム検索の公開投稿。AIで分類。詳細はサイト内の免責事項を参照。」

---

### 型B：テーマ横断まとめ

「SNS反応まっぷで扱っている11テーマを比べてみた」など。

**例：**
- 「2026年上半期、SNSで繰り返し語られた社会問題の論点」
- 「若者と高齢者で意見が分かれる社会問題、SNS投稿で可視化した5テーマ」

## UTM ルール（必須）

note 記事からサイトへのリンクには必ず UTM を付ける。

```
https://sns-reaction-map.jp/<theme>-reaction-map.html
  ?utm_source=note
  &utm_medium=referral
  &utm_campaign=note_<theme>_<yyyymmdd>
```

例：
```
https://sns-reaction-map.jp/ai-copyright-reaction-map.html?utm_source=note&utm_medium=referral&utm_campaign=note_ai_copyright_20260820
```

- `utm_source=note` 固定
- `utm_medium=referral` 固定
- `utm_campaign=note_<theme>_<yyyymmdd>` で記事・日付を特定できるようにする

GA4 で `sessionSource=note` として計測される。

---

## タイトルの SEO ルール

- **検索クエリを想像してタイトルに入れる**
  「AI著作権 SNS 意見」「高齢者免許返納 賛否」など、検索されそうな単語を先頭に置く
- **数字を入れる**（「600件」「3つの論点」など）
- **疑問形・断定形はどちらでも可**。「〇〇は正しいか」より「〇〇を分析した」が信頼されやすい
- タイトルは40字以内が目安

## 記事ごとのチェックリスト

投稿前：
- [ ] UTM 付きリンクが記事内に最低1箇所入っている
- [ ] スタンスマップの画像を貼っている（ビジュアルで差別化）
- [ ] 注記（データ源・AI分類・サンプルの限界）を入れている
- [ ] タイトルに数字または検索クエリが含まれている

投稿後：
- [ ] `content/note/posts.md` に記録した（記事 URL・UTM・公開日）
- [ ] 7日後に GA4 の `note` 流入を確認して記録した
- [ ] X告知が読者の理解に役立つ場合だけ、承認を得て候補にする
- [ ] `company/QUALITY_GATE.md` のnote確認を満たし、CEO承認を `company/APPROVALS.yaml` に記録した

## 計測方法

GA4 フィルタ：`sessionSource` = `note`

週次の KPI スナップショット時に、note 流入セッション数を確認する。
目標は月2〜3記事で月10セッション以上（半年以内）。

GSC で note ドメインからの被リンクが入ると権威性が上がる。
ただし GSC の「リンク」レポートに反映されるまで数週間かかる。

---

## 優先順位

`company/HANDOFFS.yaml` の期日と、テーマ更新・一次資料の有無を優先する。
アクセス見込みだけでテーマを選ばず、「その意見の背景を理解する助けになるか」を最初に確認する。

---

## 下書きの渡し方

1. **下書きは `content/note/drafts/` に保存する。** MarkdownまたはHTMLを使い、CEOが内容を確認できる形にする。
2. **画像は `content/note/drafts/images/<theme>_map.png` に保存する。** 画像内の重要情報は本文でも説明する。
3. **投稿後の記録は `content/note/posts.md` に書く**（記事URL・UTM・公開日）。下書きと公開実績を混ぜない。

---

## 記事の更新ルール

**更新するのは「新論点が出たとき」だけ。** 数字の差し替え（件数が増えただけ）では更新しない。

更新する条件:
- 新しい論点が浮上した
- 既存論点の比率が前回と比べて ±5pt 以上変化した
- 社会的に話題が再燃して、記事の結論が変わる可能性がある

更新するときは「前回からの変化」を1セクション追記する形にする（上書きではなく追記）。

---

## X 告知連携

note に記事を投稿したら、**投稿当日〜翌日に x-daily スキルの URL 付き投稿枠（週1〜2本）で告知する**。
note 記事の URL を貼ることで「X → note → サイト」という二段階の流入導線ができる。

## 消費税減税の既存記事について

GA4 に `consumption_tax_01` の流入が1件あるが、投稿者・URL・公開日が不明。
**既存記事とはみなさず、新規に1本書く。** 万一同テーマで2記事になってもキーワードカニバリゼーションの害は軽微と判断。

## 禁止事項

- サイトのトップページ（`/sns-reaction-map/`）だけにリンクしない。**必ずテーマページに飛ばす**
- UTM なしのリンクを貼らない（計測できなくなる）
- 「このサイトを見てください」という宣伝文だけの記事を書かない
- 他人の意見・投稿内容を引用するときは原文をそのまま載せない（要約・匿名化）
- 「あなたはどっち？」「意見が真っ二つ」など、二択や対立をあおる表現を使わない
- 収益化のために、断定・不安・個人攻撃で読ませない
- **意見のない記事を出さない。** 論点と件数を並べただけの記事はサイトの複製であり、noteに置く意味がない
- **調べた手順の順に書かない**（収集→分類→再読→検証の順に書き始めたら、構成を組み直す）
