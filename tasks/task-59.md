# 課題59: 複数テーマ更新を1つの公開候補として統合する


**状態**: 進行中（汎用の複数run-id統合・manifest化・混在適用の拒否は実装・テスト済み。DATA_REFRESH.mdへの手順化も完了。実データでの実地使用が残る）
**優先度**: 高
**判断待ち**: なし
**関連テーマ**: 全テーマのデータ更新・公開

**概要**: `refresh_topic.py --prepare-promotion` は、テーマ固有の正典とページだけでなく、トップページ、公開データcatalog、全テーマの公開JSON、サイトマップ、テーマ台帳も候補に含める。複数テーマを同日に個別に候補化すると、後から適用した候補が先に適用したテーマの全体集計を古い値へ戻す。

**やること**:

1. 複数の `run-id` を指定して、テーマ固有の正典・検証データ・ページを1つの候補ツリーへ統合する機能を追加する — **2026-09-21実装**
2. 統合後に公開JSON、catalog、トップ、SEO、sitemapを一度だけ再生成する — **2026-09-21実装**
3. 統合候補のmanifestに全対象テーマ・run-id・ハッシュを記録し、個別候補の混在適用を拒否する — **2026-09-21実装**
4. 3テーマ同時更新の自動テストを追加し、どの適用順でも数値が巻き戻らないことを検査する — **2026-09-21実装（合成データによる2テーマ検証。実データでの3テーマ検証はまだ）**

**完了条件**: 同日複数テーマの収集回を1つの承認・公開単位として候補化でき、個別候補の順次適用では公開が停止する。

## 2026-09-21: 汎用の複数テーマ統合を実装

`scripts/refresh_topic.py` に3つの関数を追加した（既存の単独テーマ用関数は無変更）:

- `prepare_public_candidate_bundle_multi`: 複数テーマぶんの正典・ページ・THEMES.yaml更新を
  1つの隔離コピーへ先にまとめてから、共有ファイル（トップ・catalog・sitemap等）の再生成を
  テーマ数に関わらず1回だけ実行する。共有スクリプト（`sync_issue_counts.py`等）はもともと
  「今のTHEMES.yaml全体を読み直して作り直す」設計だったため、再生成ロジック自体は変更せず、
  呼び出す前に全テーマの変更を1か所へ集める順序に変えただけで済んだ
- `prepare_multi_promotion_manifest` / `load_multi_promotion_manifest`: 単独テーマ版の
  manifest（topic/run_idを単数で持つ）を拡張し、`topics`を配列で持たせた。適用時に
  この配列が要求と完全一致しない場合（テーマが一部欠けている、run_idが違う等）は
  「個別候補の混在適用」として拒否する

新規CLI: `scripts/promote_multi_topics.py`（`--prepare`で候補・manifest作成、`--apply`で承認後の反映）。
既存の `refresh_topic.py --topic X --resume` で作った各テーマの保存済み更新回
（`.staging/refresh/<topic>/<run-id>/`にcumulative-candidate.json・report.jsonがある状態）を
入力に取る。個別テーマの`--prepare-promotion`は経由しない（そちらを経由すると単独テーマ版の
manifestができてしまい、今回の統合の対象にならないため）。

**テスト**: `tests/test_refresh_topic.py`に`MultiTopicPromotionTests`（5件）を追加。
2つの合成テーマで、共有再生成が1回だけ呼ばれること・両テーマの更新が同じ候補コピーへ
反映されること・準備→適用の一往復・テーマ欠落や不明テーマを混ぜた適用要求の拒否・
承認後の改変検知・入力順序を入れ替えても結果が同じであること、を検査している。
既存の単独テーマ版テスト（`RefreshTopicTests`等、53件）は無変更で全件通過を確認済み。

## 2026-09-21: DATA_REFRESH.mdへ手順化

「公開まで行う更新」節の直後に「同じ日に2テーマ以上を公開する」小節を新設し、
なぜ個別に`--prepare-promotion`してはいけないか・`promote_multi_topics.py`の
`--prepare`/`--apply`の使い方・1テーマだけなら従来どおりでよいこと、を明記した。

**関連スキルへの反映は調査した結果、対象が無いと判断した。** `.claude/skills/`配下で
`refresh_topic.py`に触れているのは`taxonomy-migration`（無関係な別バグの話）と
`x-daily`の収集連携（`--promote`系のフラグを使わず収集止まりのため対象外）の2件のみで、
公開（promotion）手順そのものを説明しているスキルは無かった。`DATA_REFRESH.md`が
この手順の唯一の正典であることを確認済み。

**残っている作業**:
- **実データでの実地使用はまだ**。今回のテストはすべて合成データによるもので、実際に2テーマ以上を
  同日に更新する場面が来たときに初めて実地検証できる
- **既存の単独テーマ用`--prepare-promotion`/`--apply-promotion`経路は今回変更していない**。
  そのため、今回作った安全な統合経路を使わず、従来どおり2テーマを別々に`--apply-promotion`
  することも技術的には引き続き可能なまま（止める仕組みは無い）。手順書への明記が唯一の
  防止策で、今回のコード変更だけでは強制できない
