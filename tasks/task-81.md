## 2026-09-21: 背景と検討の経緯

オーナーから「このプロジェクトのデータ収集作業を、毎日行っているX投稿候補作成で一緒に行う方法を考えて」と
相談があった。両者は現状まったく別の仕組みで動いている。

| | データ収集（`DATA_REFRESH.md`） | X日次運用（`.claude/skills/x-daily/`） |
|---|---|---|
| 頻度 | テーマごとに`THEMES.yaml`の`collect_at`で管理。全11テーマがおおむね7日周期（自転車のみ14日） | 毎日（呼ばれたときだけ動く。自動cronではない） |
| 場所 | 専用worktree必須（非公開正典の復元・`node_modules`の複製が要る） | 準備不要。ブラウザでXを見るだけ |
| 手段 | `scripts/fetch_yahoo_realtime_node.mjs`でYahoo!リアルタイム検索からX投稿を自動収集し、hermes（`kimi-k2.6`、OpenCode Go経由）で自動分類 | 人（AI）がXを直接検索し、1件ずつ内容適合を判定 |

### 却下した案: 収集の全工程を毎日一緒に回す

本文確認・正典反映・公開まで含む全16ステップ（`DATA_REFRESH.md`「定期更新1回分の実務手順」）を毎日の
X日次に混ぜると、軽い日次作業に重い前提（worktree・private data復元）が常時乗ってしまう。
OPERATIONS.mdが明示的に廃止した「毎朝7時の自動タスク`daily-growth-loop`」（45日間気づかれず停止）と
同じ失敗パターンに戻るリスクがあるため却下。

### 採用した案: 「収集の最初の一歩（収集・自動分類・非公開保存）」だけをX日次の頭に足す

`refresh_topic.py --topic <テーマ>`を`--promote`なしで実行するステップ（`DATA_REFRESH.md`の16ステップ中の
1のみ）を、X日次の「開始時の確認」に追加する。

**2026-09-21 追記: レビューで3点の抜けが見つかり、手順に反映した（0・3・4に反映）。**
X日次は1日1回ではなく、朝・昼・夕・夜など**1日に複数回（目安4回）呼ばれる運用が通常**と
オーナーに確認できた（`OPERATIONS.md`の「毎日」という記載だけでは分からなかった）。
この前提が無いと、以下がそのまま起きる。

- 収集した記録がmainへ届かないと、呼ばれるたびに「まだ収集していない」と見え、
  同じテーマを何度も収集し直す
- 期限超過テーマが複数ある日（2026-09-20時点で3テーマ同時超過の実例あり）は、
  朝・昼・夕・夜がそれぞれ別テーマを拾い、「今日の負荷は一定にする」つもりが
  呼び出し回数ぶん動いてしまう
- worktree（作業用のコピー）を「本文確認・公開が終わるまで残す」設計のまま
  新規作成を続けると、片付けの遅い本文確認・公開に対して増える一方になる
  （2026-09-21時点で他テーマ分だけで25個残っている実態を確認済み）

0. **今日すでに収集済みか確認する。** `THEMES.yaml`の全テーマの`last_refresh_attempt_at`を見る。
   いずれかが今日の日付なら、収集ステップ（1〜4）はスキップして6（候補作成）へ進む。
   （課題69など、X日次を経由しない収集がその日すでに走っていた場合も、このチェックで自然に
   二重収集を避けられる）
1. `build_admin_dashboard.py`で収集遅れを確認（既存のOPERATIONS.md ⓪の入口と同じ）
2. `collect_at`を過ぎている／当日のテーマがあれば、最も遅れている**1本だけ**を選ぶ
   （複数まとめない。期限超過が積み上がっている日でも今日の負荷は一定にする）
3. **そのテーマの収集専用worktreeが既に存在するか確認する。** 前回収集した分がまだ
   本文確認・公開を終えていない場合は新規に作らず使い回す（`git -C <worktree> fetch origin &&
   git -C <worktree> merge origin/main`で最新へ追いつかせてから使う）。無ければ
   `../isa-wt-collect-<テーマ>`（ブランチ`task/collect-<テーマ>`）という固定名で新規作成する
   （固定名にしないと、後から「このテーマの収集worktreeがどれか」を探せない）。
   ここで`refresh_topic.py --topic <テーマ>`（`--promote`なし）を実行する。正典・公開ページには触れない
4. `THEMES.yaml`等をコミットし、`themes/{テーマ}.md`に一言記録。**その直後、下記「収集直後のmain反映」
   手順でmainへマージ・pushする。** worktree自体は、本文確認・公開のときに非公開データの復元を
   やり直さずに済むよう残す（＝worktreeを残す理由は「あとで使い回す」だけになり、
   「収集した」という記録は毎回mainへ届く）。本文確認・公開はこれまで通り別セッション・低頻度で
   進める。課題69の「1テーマずつ」運用は変えない
5. 直近{n}日で収集・公開したテーマがあれば、その回で分かった変化を本日の論点ポストの優先ネタにする。
   `X_POSTING_GUIDE.md`§5「どのテーマを投稿するか」に「直近収集」の基準が無いことに気づいた。
   `GROWTH.yaml`の`recurring.x-posting`にも`per-theme-publish（告知）`という項目名だけあり、
   具体的な手順が無い空白だった
6. いつも通りX日次の候補作成に入る
7. **収集が途中で失敗した場合**（外付けバックアップディスク未接続・hermes障害・`node_modules`
   不足など、`DATA_REFRESH.md`に前例あり）は、その日の収集は見送ったものとして6（候補作成）へ
   進む。X日次側では無理に復旧を試みない

### 収集直後のmain反映（ステップ4の詳細、2026-09-21追記）

収集だけ（`--promote`なし）なので公開ページは変わらない。ページの整合性検査一式
（`release`スキルが使う`verify_theme_page.py`等）は的外れで時間もかかるため、ここでは
収集の記録（`THEMES.yaml`・`themes/{テーマ}.md`・`data/verification/updates/`）だけを
対象にした軽量版にする。**`release`スキルそのものではなく、その一部を流用した新設の手順で、
実際に1回動かして問題が無いか未確認**（下記「未確認・次に測ること」に追記）。

```sh
# 共有ツリーで、収集worktreeのブランチをマージする
cd /Volumes/M2-WorkSpace/Projects/副業/issue-stance-aggregator
git merge --no-ff task/collect-<テーマ> -m "Merge branch 'task/collect-<テーマ>'"
python3 scripts/verify_themes_yaml.py
python3 scripts/verify_update_provenance.py
git push
```

検査は`release`スキルの規定どおり**マージした後のmainで**通す（作業ツリーで通したかどうかは
根拠にならない）。成功の形: `git merge`が`Merge made by the 'ort' strategy.`、
2つの`verify_*.py`がともに終了コード0、`git push`が`main -> main`の行を出す。
衝突したら`release`スキルの規定どおりその場で直さずオーナーへ報告する。検査で落ちたら、
収集worktree側で直してコミットし直し、マージからやり直す。

`social-samples/`配下の非公開データは収集worktreeに残したままでよい（`refresh_topic.py`が
更新回確定時に自動でバックアップ済み）。公開ページに触れていないため、`release`スキルの
②（共有ツリーへのrsync）は本文確認・公開のタイミングでまとめて行えば足りる。

### 付ける場所は `x-daily-measure`（自動cron）ではなく `x-daily`（呼ばれて動く候補作成）側

`x-daily-measure`は毎日20:05に**無人で**自動実行される（`mcp__scheduled-tasks__list_scheduled_tasks`で確認済み）。
ここに収集（worktree作成・スクレイピング・hermes呼び出し）のような重い処理を足すと、無人実行中に
失敗しても誰も気づけない。X日次（候補作成）は元々人（AI）が呼んで動かすため、その場で異常に気づける。

### 実測した数値

- **テーマ数と周期**: 全11テーマ、収集間隔はほぼ7日（自転車のみ14日）。2026-09-20時点で3テーマが
  すでに期限超過（takaichi 24日・elderly-license-revocation 9日・ai-copyright 8日）。
  11テーマ×週1回ペースなら、ほぼ毎日どこかのテーマが対象になる
- **「収集だけ」の所要時間**（2026-08-20 elderly-license-revocationの`report.json`実績）:
  smoke 7秒＋fetch 55秒＋分類923秒（約15分）。ほぼ待ち時間で、合計約16分
- **worktree準備の所要時間**: 非公開データのバックアップ約14MB、`node_modules`約17MB。
  tar展開・コピーとも数分規模（体感、秒単位の計測はしていない）

### この案の範囲（スコープ）

**やる**: 収集（Yahoo!リアルタイム検索経由のスクレイピング）→ hermesによる自動分類（`kimi-k2.6`）→
非公開の作業用フォルダへの保存 → `THEMES.yaml`の収集試行日時更新

**やらない**: 正典への反映、公開ページの更新、本文確認（人が1件ずつ読む工程）。`refresh_topic.py`に
「収集だけ・分類は後回し」という選択肢（`--skip-classify`等）は無く、分類はセットで実行される
