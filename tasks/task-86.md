# 課題86: 更新作業（本文確認→公開）の遅れを自動で報告する

**状態**: 進行中。自動タスク`update-work-check`を新設（2026-09-22）。実際に本文確認・公開の
セッションをどの頻度で行うかは未確定
**優先度**: 中。収集（課題81）が仕組み化された分、更新作業側が追いつかないと
「収集済みだが未公開」のデータが静かに溜まるリスクがある
**関連**: 81（X日次運用へのテーマ収集組み込み。収集側の同型の課題）/ 69（定期データ更新の
通常運用の型を確立する。本文確認→公開そのものの手順）

## 何を解決するか

課題81で収集のタイミングは決まったが、その後工程（本文確認→正典反映→公開、
「更新作業」）のタイミングは決まっていなかった。`OPERATIONS.md`の定例作業表で、
頻度が空欄なのはこの行だけだった。

収集は夜枠固定・15〜20分・人の判断不要で仕組み化できたが、更新作業は性質が違う。
本文を1件ずつ人が読んで判定する工程（`DATA_REFRESH.md`の「徹底事項」:
「自動判定プログラムに置き換えない」——消費税減税の要約使い回し事故の教訓）で、
最後は必ずCEO（オーナー）承認が要る。だから収集と同じ「夜枠に自動で差し込む」は使えない。

## 検討した案と却下理由

**却下: x-daily-measureと同じ形で本文確認〜公開まで自動化する。**
本文確認はルール上、自動判定に置き換えられない。公開の最終承認もオーナーの役割
（`company/COMPANY.md`「権限の原則」）。両方とも意図的な人間ゲートであり、
自動化するとこれらの安全策を無効化することになる。

**却下: `manage_reread_registry.py prepare`を定期的に自動実行する。**
`prepare`は「読む対象を固定する」操作で、`--out`に指定した保存先が既に存在すると
エラーになる（同じ対象を2度固定できない設計。ソース確認済み）。1日1回程度の自動再実行を
想定した作りではなく、実際に読む人が着手する直前に1回だけ呼ぶのが正しい使い方。定期的に
呼ぶと、誰も`record`で確定しないまま固定対象ファイルだけが溜まる。

**採用: 「遅れの報告だけ」を自動化する。** `refresh_at`が一番遅れているテーマを
報告する。本文は読まない・`prepare`も呼ばない・公開もしない。
実際に読む・公開するかどうかの判断と実行は、人間参加のセッションに委ねる。

**頻度は「2日に1回」ではなく「毎日」で実装した。** 標準cron（5フィールド）の
`日` 欄は暦日の絶対値（1・3・5…）にしか一致できず、「今日から2日おき」を表現できない。
`*/2 * *`で作成したところ、登録した当日（9/22、偶数日）が対象外になり「次回実行は明日」
と表示された（今夜動かしたいというオーナーの要望に反する）。このタスクは本文を読まない
読み取り専用の報告なので、頻度を上げても実害が無い。日付境界の癖に対応する専用ロジックを
足すより、単純に毎日にする方が安全で分かりやすいと判断した。

## 2026-09-25: 収集と公開を同じセッションで行う運用へ変更（オーナー決定）

- 発端: 9/25の自動報告で「更新作業の期限」とされた皇室典範・憲法改正は、どちらも
  前回の収集分がすでに公開済みで、やることが無かった。原因は、`refresh_at`（公開予定日）が
  公開時に、`collect_at`（収集予定日）が収集時に、それぞれ別々に進む作りで、
  公開予定日が次の収集より先に来ていたこと（10テーマ中6テーマで2〜3日ずれていた）
- オーナー決定: 収集と公開は必ず同じセッションで行う。公開直前に同じセッションで承認を取る。
  その日に公開できなければ予定日を進めず、次回は新しく集めずにその回を仕上げる。
  X日次の夜枠収集は廃止し、22時の自動報告は作り直す
- 実装: `refresh_topic.py` は収集だけでは `collect_at` を進めず `pending_wave` を残す。
  公開時に `collect_at`=`refresh_at` をそろえて進め `pending_wave` を消す。
  `pending_wave` があるテーマは `--resume` なしの収集を止める。
  新規0件・`--allow-taxonomy-mismatch` の回だけは収集時点で予定日を進める
- 検査: `tests/test_refresh_topic.py` の `test_registry_keeps_collect_and_refresh_on_the_same_date`
  が THEMES.yaml の日付のずれを落とす。管理画面は `pending_wave` のテーマを
  「収集済みの回を公開まで。新しく集めない」と表示する
- 既存6テーマの `refresh_at` を `collect_at` にそろえた（全10テーマの最新収集分が
  正典に入っていることを確認してから）。上の「本文確認・公開のセッション頻度」は、
  収集予定日（既定14日、新規意見50件以上なら7日）に従う形で解消した
