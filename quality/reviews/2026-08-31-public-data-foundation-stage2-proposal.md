# 課題57 段階2：公開データ契約の提案

作成日: 2026-08-31  
状態: 独立レビュー・CEO確認前の提案。公開物は変更していない。

## CEOに確認したい結論

公開ページに使う数字を、今後はテーマごとの公開JSONと全テーマのcatalogだけから出す。
読者に見せる用語は、次の4つに固定する。

| 用語 | 意味 |
|---|---|
| 収集した投稿 | 重複を除いて保存した公開投稿の数 |
| 分析対象の意見 | 分類で意見と判定した投稿の数 |
| 主要論点 | 「その他」を除き、表示する名前付き論点 |
| その他 | 主要論点には含めないが、分析対象の意見から除外しない分類 |

「分類済み投稿」は総数ラベルとして廃止する。投稿本文、投稿ID、利用者情報、個別ハッシュ、AIの信頼度、
内部の判断理由は公開JSONに入れない。

## 仕様ファイル

- `schemas/public-theme.schema.json`: 1テーマの公開集計
- `schemas/public-catalog.schema.json`: 公開テーマ一覧・トップ・sitemap用集計

いずれも `schema_version: "1.0"` を必須とし、想定外の項目を受け付けない。catalogに生成時刻を
入れないため、同じテーマJSONから2回生成しても差分が出ない。

## 必ず検査する条件

JSON Schemaで型・必須項目・公開禁止項目を、生成器の検査で次を確認する。

1. `collected_count >= opinion_count`
2. `issue_assigned_count == opinion_count`
3. 論点の件数合計が `issue_assigned_count` と一致する
4. 各論点で、立場別件数と表現強度別件数が論点件数と一致する
5. `kind: other` は各テーマに最大1つ。`named_issue_count` には含めない
6. 収集期間が分からない場合は日付を推測せず、`status: "unknown"` として開始・終了を `null` にする
7. `THEMES.yaml` が `published: done` のテーマだけをcatalogに入れる

JSON Schemaだけでは「配列中の数値合計」を表現できないため、1〜5は専用検査器で必ず失敗扱いにする。

## 固定IDの方針

論点・立場のIDは表示名から自動で作らない。各テーマ設定に明示し、表示名を直してもIDは変えない。

- 形式: `テーマID-英字の意味ID`（例: `bukatsu-chiiki-kyoin`）
- 論点「その他」は必ず `kind: other`
- 立場のIDは、テーマ内で一意の英字IDにする
- 既存投票の `topicId`・選択肢の順序は変更しない。公開データIDは投票の保存番号ではない

部活動テーマの既存 `configs/planet/bukatsu-chiiki.yaml` はこの考え方の参考にするが、
課題54用の地形設定を公開データJSONの入力にはしない。10テーマ分の固定ID対応表は、
この提案の承認後に各 `configs/*-reaction-map.json` へ追加する。

## 段階1で判明した例外

自転車青切符の累積正典は `is_opinion` をレコード直下に置く一方、他テーマの多くは
`classification` 内に置く。生成器は保存場所ではなく、既存の正規化規則で同じ「分析対象の意見」を数える。
この互換処理を入れずに、データの再分類は行わない。

## CEO確認後の作業

1. 10テーマの論点・立場ID対応をテーマ設定へ明示する
2. Schemaと上記不変条件を検査する生成器を、部活動テーマだけで実装・照合する
3. 独立レビューで、公開禁止情報・古いHTML／SQLite／旧ルートからの逆流がないことを確認する
