# 課題57 段階2：公開データ契約の提案

作成日: 2026-08-31  
状態: CEO確認・Claude独立レビュー・指摘修正済み。公開物は変更していない。

## CEOに確認したい結論

公開ページに使う数字を、今後はテーマごとの公開JSONと全テーマのcatalogだけから出す。
読者に見せる用語は、次の4つに固定する。

| 用語 | 意味 |
|---|---|
| 収集した投稿 | 重複を除いて保存した公開投稿の数 |
| 分析対象の意見 | 分類で意見と判定した投稿の数 |
| 主要論点 | 「その他」を除き、表示する名前付き論点 |
| その他 | 主要論点には含めないが、分析対象の意見から除外しない分類 |

「分類済み投稿」は総数ラベルとして廃止する。投稿本文、投稿ID、利用者情報、個別ハッシュ、AIの信頼度、
内部の判断理由は公開JSONに入れない。

## 仕様ファイル

- `schemas/public-theme.schema.json`: 1テーマの公開集計
- `schemas/public-catalog.schema.json`: 公開テーマ一覧・トップ・sitemap用集計

いずれも `schema_version: "1.0"` を必須とし、想定外の項目を受け付けない。catalogに生成時刻を
入れないため、同じテーマJSONから2回生成しても差分が出ない。

## 必ず検査する条件

JSON Schemaで型・必須項目・公開禁止項目を、生成器の検査で次を確認する。

1. `collected_count >= opinion_count`
2. `issue_assigned_count == opinion_count`
3. 論点の件数合計が `issue_assigned_count` と一致する
4. 各論点で、立場別件数と表現強度別件数が論点件数と一致する
5. `kind: other` は各テーマに最大1つ。`named_issue_count` には含めない
6. 収集期間が分からない場合は日付を推測せず、`status: "unknown"` として開始・終了を `null` にする
7. `THEMES.yaml` が `published: done` のテーマだけをcatalogに入れる
8. catalogの `theme_id`、テーマ内の `issue.id`、各論点内の `stance.id` は、それぞれ重複を禁止する
9. catalogの合計（テーマ数・収集数・意見数・最終更新日）は、テーマ配列から再計算した値と一致させる
10. 分類結果に固定ID対応表にない論点・立場が1件でもあれば、黙って除外せず生成を失敗させる
11. `kind: other` は全テーマの設定に必ず1つ置く。現在0件でも削除しない

JSON Schemaだけでは「配列中の数値合計」や配列をまたぐ一意性を表現できないため、1〜11のうち
構造検査だけで保証できないものは専用検査器で必ず失敗扱いにする。

## 決定的な生成とハッシュ

同じ入力からは必ず同じバイト列を出す。生成器は次の規則を固定する。

1. 非公開正典は、レコード内のオブジェクトキーを辞書順にし、レコードを既存の決定的な投稿識別規則で並べ、
   UTF-8・改行LF・余分な空白なしで正規化する。そのバイト列のSHA-256を `source_sha256` とする
2. `data_version` は `v1-` と `source_sha256` の先頭16文字を連結する。生成時刻を使わない
3. 公開テーマJSONはキーを辞書順、論点・立場は固定ID設定順、強度は `low`・`medium`・`high` 順、
   UTF-8・改行LF・末尾改行1つで出力する
4. catalogのテーマ順は `theme_id` の辞書順に固定する。`data_sha256` は公開テーマJSONの出力バイト列、
   `generated_from` は `theme_id:data_sha256` をテーマ順に改行結合したバイト列のSHA-256とする

## 収集期間の変換

- `YYYY-MM-DD〜YYYY-MM-DD` は `status: known` とし、開始・終了へそのまま入れる
- 単一の `YYYY-MM-DD` は開始日だけが確認された記録として `status: start_only`、`start` に日付、`end` は `null` とする
- `unknown` または欠落は `status: unknown` とし、開始・終了をともに `null` にする
- `sample_period_source` が無い日付を推測して補わない

## 固定IDの方針

論点・立場のIDは表示名から自動で作らない。各テーマ設定に明示し、表示名を直してもIDは変えない。

- 形式: `テーマID-英字の意味ID`（例: `bukatsu-chiiki-kyoin`）
- 論点「その他」は必ず `kind: other`
- 立場のIDは、テーマ内で一意の英字IDにする
- 既存投票の `topicId`・選択肢の順序は変更しない。公開データIDは投票の保存番号ではない

部活動テーマの既存 `configs/planet/bukatsu-chiiki.yaml` はこの考え方の参考にするが、
課題54用の地形設定を公開データJSONの入力にはしない。CEO承認後、10テーマ分の固定ID対応表を
専用のテーマ設定 `configs/public-data-taxonomy.json` に追加した。このファイルは表示名からIDを
生成せず、分類ラベルと固定IDを明示対応させる。

## 段階1で判明した例外

自転車青切符の累積正典は `is_opinion` をレコード直下に置く一方、他テーマの多くは
`classification` 内に置く。生成器は保存場所ではなく、既存の正規化規則で同じ「分析対象の意見」を数える。
この互換処理を入れずに、データの再分類は行わない。
