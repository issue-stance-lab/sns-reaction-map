## 1. 結論

課題15-Aを課題57へ統合し、公開10テーマの数字・用語・更新日・論点を、
同じ公開データ契約から再生成できる状態にする。

問題はデータベースが無いことではなく、同じ数字・用語・日付を複数のファイルや生成器で
手編集できることである。Git管理のJSONを公開用のデータ契約にし、トップ、10テーマ、
サイトマップ、将来の3D用データが同じ契約を読むようにする。

課題57では3Dを実装しない。課題57の完了後に課題54で部活動の地域移行から3Dを作り、
一般公開とSearch Console確認は15-Cで行う。

## 2. 正典の分担

| 事実 | 正典 | 備考 |
|---|---|---|
| 投稿本文・投稿ID・AI分類 | `social-samples/` | 非公開。バックアップから復元する |
| 公開状態・ファイル位置・更新予定 | `THEMES.yaml` | 公開対象は `published: done` だけで判定 |
| 質問・説明文・安定した論点／立場ID | テーマ設定 | 表示名変更でIDを変えない |
| 公開可能な集計値 | `data/public/themes/*.json` | 生成専用。手編集禁止 |
| 公開10テーマ一覧・全体集計 | `data/public/catalog.json` | 自動生成 |
| HTML・3D用JSON・sitemap・robots | `docs/` | 生成物。次回生成の入力にしない |

公開データJSONは、公開レンダラーにとって唯一の**構造化データ入力**とする。
説明文、一次資料、テンプレートは別の正典として残し、「JSONだけが全ページの唯一の入力」とはしない。

### 2.1 公開テーマJSONの必須項目

- テーマID、タイトル、問い、公開ページパス
- 読者向け更新日、収集期間、データ版
- `collected_count`: 重複除外後に保存した収集投稿数
- `opinion_count`: 意見と判定した投稿数
- `issue_assigned_count`: 主要論点または「その他」へ割り当てた意見数
- 論点ごとの安定ID、表示名、`kind: named | other`、件数
- 論点内の立場別件数、表現強度別件数
- 正規化した非公開正典全体のSHA-256
- スキーマ、分類体系、生成器の版

投稿本文、投稿ID、レコード単位のハッシュ、ユーザーID、AI confidence、内部理由は含めない。

### 2.2 数字の不変条件

- `collected_count >= opinion_count`
- 全意見を主要論点または「その他」へ割り当て、`issue_assigned_count == opinion_count`
- 論点別件数の合計は `issue_assigned_count` と一致する
- 各論点の立場別件数合計は、その論点の件数と一致する
- 各論点の強度別件数合計は、その論点の件数と一致する
- 期間不明は推測せず `null` と根拠状態を記録する
- 「その他」は内部の論点区分には含め、読者には「主要K論点＋その他」と分けて表示する

### 2.3 読者向け用語

- 収集した投稿
- 分析対象の意見
- 主要論点
- その他

意味が曖昧な「分類済み投稿」は総数ラベルとして使わない。

1. 公開テーマJSONとcatalogのJSON Schemaを作る。
2. 論点・立場IDを表示名から自動生成せず、テーマ設定に明示する。
3. 「その他」は `kind: other` として主要論点から区別する。

5. 表現強度分布を持たせ、課題54の標高計算へ流用できる形にする。

### 段階3：公開データ生成器を作る

1. `build_public_registry.py --all` で非公開正典から公開JSONを生成する。
2. `verify_public_registry.py --public-only` でSchemaと公開データ内の整合を検査する。
3. `verify_public_registry.py --against-private` で非公開正典と完全照合する。
4. 完全照合の終了コードを `0=一致`、`1=不一致`、`2=非公開正典なし` に固定する。
5. 最初に部活動の地域移行だけを生成・完全照合する。3Dは作らない。
6. 部活で契約が成立したら、残り9テーマを生成する。
7. catalogは `published: done` と公開JSONから生成し、高市テーマを除外する。
8. 同じ入力から2回生成し、差分0を確認する。

**成功条件**:

- 公開10テーマのJSONとcatalogが生成される
- 非公開正典が無い環境でも、コミット済み公開JSONから公開物を再生成できる
- 非公開正典が無い状態を完全監査成功として扱わない

- `docs/` を次回生成の入力にする処理がない

### 段階5：通常のデータ更新へ接続する

1. `refresh_topic.py` の公開候補作成を次の順へ統一する。
   非公開正典候補 → 公開JSON候補 → テーマHTML候補 → トップ・sitemap候補 → 完全監査 → manifest。
2. 公開JSON、HTML、sitemapの一部だけが更新される状態を禁止する。
3. 期限超過などの運用警告と、公開を止める検査失敗を別表示にする。
4. 既存のpromotion manifestへ公開データと `docs/` のハッシュを含め、別のmanifestを重複新設しない。
5. 承認後は再生成せず、manifestに固定された候補を適用する。

**成功条件**:

- 1テーマの更新で公開JSON、ページ、トップ、sitemapが同時に候補化される
- 一部だけ古い状態では昇格できない
- 承認対象と適用対象が同じハッシュで結ばれる
