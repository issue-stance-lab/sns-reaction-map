## 1. オーナー向けの結論

問題の中心は、単にリポジトリが2つあったことではない。

同じ数字・用語・URLが、非公開データ、`THEMES.yaml`、設定ファイル、生成スクリプト、公開HTML、
サイトマップなどへ重複して書かれ、一部を手で直せることが再発原因である。データベースを1つ追加するだけでは、
その外側に手編集できる数字が残れば同じ事故が起きる。

最終案は、次の4点を一体で実施する。

1. **公開データ台帳を1つにする** — 公開してよい数字・論点・日付を、Gitで差分確認できるJSONへ集約する
2. **公開物を1本の生成経路にする** — トップ、10テーマ、3D用データ、サイトマップを同じ台帳から作る
3. **承認対象を固定する** — CEOが確認した生成物と、実際に公開する生成物を同じハッシュで結ぶ
4. **公開元を1つにする** — `issue-stance-lab/sns-reaction-map` だけを正式な公開元として使う

データベースについては、**Git管理のJSONを公開正典にし、SQLiteは必要なら検索用に毎回作り直す**構成を採用する。
いまSupabaseや外部データベースへ全面移行する案は採用しない。静的サイトの規模では運用負荷が増え、
「どの時点の数字を誰が承認したか」をGit差分で確認しにくくなるためである。

## 2. 現在確認できる問題

### 2.1 数字の正典はあるが、公開までの経路が複数ある

- 投稿本文を含む非公開正典は `social-samples/` にある
- 公開テーマ判定、更新日、取得期間などは `THEMES.yaml` にある
- 論点名や表示文はテーマ別configやテーマ固有ビルダーにもある
- 公開HTMLにも数字・日付・ラベルが焼き込まれている
- テーマごとに生成方法が異なり、一部の補助スクリプトは別テーマまで巻き戻す危険がある
- `docs/` を次回生成の入力として読む経路が残ると、古い公開値を正典へ逆流させる

課題15-Aは、この状態で表面化した数字・用語・公開テーマ・サイトマップの不一致を止めるための重要な修正である。
ただし、長期的には「検査を増やして手編集の結果を見張る」だけでなく、手編集できる場所そのものを減らす必要がある。

### 2.2 既存SQLiteは現行基盤ではない

`data/reaction_map.sqlite3` はすでに存在するが、2026-08-31時点で次の状態である。

- 登録事例は2件のみ
- 投稿494件、分類494件
- 公開対象10テーマを管理していない
- 初期コミット以降、現行の収集・分類・公開経路から参照されていない
- Git管理されたバイナリで、投稿本文494件、投稿URL494件、ユーザーID494件を含む

これは `company/FOLDER_MAP.md` の「投稿本文を含むデータは `social-samples/` で非公開保全」という現行ルールと合っていない。
**新基盤へそのまま流用しない。削除やGit履歴の書き換えも、この設計作業では行わない。**
最初に内容・バックアップ・公開履歴を監査し、CEO承認を得た別作業で扱う。

### 2.3 2リポジトリ問題の整理

2リポジトリの存在そのものが直接の原因ではないが、同じサイト内容を2か所で生成・公開していたことが、
数字・サイトマップ・更新日の不一致を増幅した。

課題55で正式公開元は `issue-stance-lab/sns-reaction-map` に一本化された。今後、旧ルートリポジトリは
案内・転送だけを担当し、テーマ数や投稿数を持たせない。公開データ基盤は正式公開元のリポジトリだけに置く。

## 3. 採用する構成

### 3.1 正典を3層に分ける

| 層 | 役割 | 保存先 | Git | 公開サイトの生成入力 |
|---|---|---|---|---|
| 非公開証拠層 | 投稿本文、投稿ID、収集語、AI分類、内部理由 | `social-samples/` と承認済みバックアップ | 管理しない | 直接は使わない |
| 公開データ層 | 公開してよい集計値、論点、スタンス、期間、データ版 | 新設する `data/public/themes/*.json` | 管理する | **唯一のデータ入力** |
| 公開物層 | HTML、3D用JSON、robots、sitemap、画像参照 | `docs/` | 管理する | 入力にしない |

非公開証拠層から公開データ層を作る際は、投稿本文、ユーザーID、内部のAI判定理由を取り除く。
公開サイトは、非公開データが無いworktreeでも公開データ層から同じ内容を再生成できるようにする。

完全監査時だけ、非公開証拠層と公開データ層を照合する。非公開正典が無い環境では監査を成功扱いにせず、
「公開物の再生成だけ可能」「正典との再照合は未実施」と明確に分ける。

### 3.3 1テーマ分の公開データ契約

各テーマのJSONは、少なくとも次を持つ。

```json
{
  "schema_version": 1,
  "theme_id": "bukatsu-chiiki",
  "publication_status": "published",
  "title": "部活動の地域移行",
  "question": "...",
  "dataset": {
    "source_fingerprint": "sha256:...",
    "classification_version": "...",
    "collected_count": 0,
    "opinion_count": 0,
    "issue_assigned_count": 0,
    "collected_from": "YYYY-MM-DD",
    "collected_to": "YYYY-MM-DD",
    "published_updated_at": "YYYY-MM-DD"
  },
  "issues": [
    {
      "id": "stable-machine-id",
      "label": "読者向け表示名",
      "opinion_count": 0,
      "stances": [
        {"id": "stable-stance-id", "label": "表示名", "count": 0}
      ]
    }
  ]
}
```

上記の数値は例示の0であり、実装時は非公開正典から計算する。現行の件数をこの設計書へ転記しない。

### 3.4 数字の定義を固定する

- `collected_count`: 検索・収集して保存した重複除外後の投稿サンプル数
- `opinion_count`: 現行ルールで「意見」と判定した投稿数
- `issue_assigned_count`: 公開論点または「その他」に割り当てた意見数
- 論点別件数の合計: `issue_assigned_count` と一致
- 各論点のスタンス件数合計: その論点の `opinion_count` と一致
- 期間不明: 推測日を入れず `null` と根拠状態を記録
- 更新日: ファイル更新日ではなく、読者向けデータが実際に更新された日

「収集」「分類」「意見」「論点分類」の語をページごとに言い換えない。表示名は共通辞書から生成する。

### 3.5 本文中の数字も参照式にする

集計値を説明文へ直接書かない。管理対象の数字は、例えば次のような参照式から埋め込む。

```text
{{ metric("dataset.opinion_count") }}
{{ metric("issues.cost.opinion_count") }}
```

例外として固定年、法令番号、金額などを文章へ書く場合は、集計値と区別できる属性または許可リストへ
出所と理由を登録する。単に数字が一致しているだけでは合格にしない。

## 4. 生成と公開の流れ

```text
非公開正典
  ↓ 集計・匿名化・スキーマ検査
公開データ台帳（10テーマ）
  ↓ 共通生成
トップ / 10テーマ / 3D用JSON / 共通ページ / sitemap / robots
  ↓ 自動検査・2回生成比較
固定された公開候補 + release-manifest
  ↓ 独立品質レビュー
CEOがコミットSHAとmanifestハッシュを承認
  ↓ 再生成せず、その成果物を公開
本番検査・Search Console確認
```

### 4.1 release-manifestに記録するもの

- リリースID
- 対象10テーマのID
- 公開データJSONのSHA-256
- 非公開正典の指紋（内容は含めない）
- 生成器のGitコミットSHA
- 公開候補に含まれる全ファイルのSHA-256
- 実行した検査名と結果
- 品質レビュー記録へのパス
- CEO承認記録へのパス

CEO承認後にmainが変わった場合は、その承認を流用しない。最新mainへ統合して公開候補を作り直し、
差分を再レビューする。承認後に生成し直して同じに見えるものを公開する運用は禁止する。

### 4.2 `docs/`の扱い

- `docs/`は公開物であり、データの正典ではない
- 生成器は`docs/`内の数字や分類を入力として読まない
- 緊急修正を除き、生成管理区画を直接編集しない
- 直接編集した場合も、次の生成前に公開データ台帳またはテンプレートへ同じ修正を戻す
- 同じ入力で2回生成し、差分が0になることを公開条件にする

## 5. 自動検査の必須項目

### 5.1 公開データ検査

- `THEMES.yaml` の `published: done` と公開データJSONがちょうど10テーマで一致する
- 非公開テーマがトップ、3D、サイトマップ、合計値へ入らない
- JSON Schemaに適合する
- テーマID、論点ID、スタンスIDが重複せず、表示名変更でもIDは変わらない
- 収集数・意見数・論点分類数の大小関係と合計が一致する
- 期間不明を推測で補完していない
- 投稿本文、ユーザーID、内部AI理由が公開データへ入っていない
- 非公開正典がある完全監査では、全集計値と指紋が一致する

### 5.2 公開物検査

- トップ、10テーマ、3D用JSON、HTMLフォールバックが同じ公開データを示す
- canonical、OGP、JSON-LD、robots、sitemapが `https://sns-reaction-map.jp/` を示す
- 旧オリジンは転送・移行記録など許可箇所以外で0件
- 生成管理区画に手書きの集計値が残っていない
- 公開HTMLを削除しても、公開データ台帳から再生成できる
- GA4、投票、AdSense、Supabase、OGP、topicIdと選択肢を壊していない
- 3Dが動かなくても同じ論点・件数・理由をHTMLで読める

### 5.3 リリース検査

- 同じ入力から2回作った公開候補のハッシュが一致する
- 公開候補の生成後に未コミット差分が残らない
- 品質レビュー対象とCEO承認対象のmanifestハッシュが一致する
- 公開されたファイルと承認済みmanifestが一致する
- 不一致時は公開を止め、前回の承認済み成果物へ戻せる

検査が一部落ちている状態を「いつもの失敗」として許容しない。期限超過など公開可否と別の警告は、
失敗と警告を別の終了コード・表示へ分ける。

## 6. 段階的な実装計画

### 段階0: 既存SQLiteの安全監査

1. `data/reaction_map.sqlite3` の内容、Git履歴、利用箇所、バックアップ有無を記録する
2. 新しい処理がこのDBを参照していないことを検査で固定する
3. 投稿本文・URL・ユーザーIDを含むため、今後の保管先と履歴対応を別のCEO承認案件にする
4. この段階ではDB削除、履歴書き換え、公開設定変更を行わない

**成功の形**: 既存DBを現行正典と誤認せず、削除・保全の判断材料が品質レビューへ出ている。

### 段階1: 公開データ契約を確定する

1. `company/FOLDER_MAP.md` に新しい公開データ層を追加する
2. JSON Schemaと用語定義を作る
3. 課題15-Aの検証用データとテストを流用できるか実ファイルで確認する
4. 公開10テーマの現行生成経路と、数字が現れる場所を一覧化する
5. 直接編集可能な数字を「台帳参照へ移す」「固定値として出所登録」「廃止」に分類する

**成功の形**: 10テーマの公開値を何から作るかが1枚の対応表で確認でき、未確認項目が0件。

### 段階2: 部活地域移行で基準実装する

1. `bukatsu-chiiki` の公開データJSONを非公開正典から生成する
2. 現行ページ、3D用planet-data、論点カード、フォールバックHTMLを同じJSONから生成する
3. 既存993意見を使う場合も、件数を設計書から転記せず実データから再計算する
4. 現行公開版との意図しない差分、投票、GA4、OGP、AdSenseを検査する
5. 2回生成の差分0と、非公開正典との完全監査を通す

**成功の形**: 部活の数字を1か所直すと全表示が同期し、HTMLを手で直す必要がない。

### 段階3: 残り9テーマへ移行する

1. テーマ固有ビルダーを一度に全廃せず、公開データJSONを受け取る互換アダプターへ順次変更する
2. 1テーマごとに公開版との比較、完全監査、再生成可能性を確認する
3. 10テーマすべてが移るまで、旧経路と新経路のどちらが正かをテーマ台帳へ明記する
4. 非公開の11件目を公開10テーマの集計へ混ぜない

**成功の形**: 公開10テーマすべてが同じ契約に適合し、テーマ固有コードに件数が残っていない。

### 段階4: リリース固定と承認を実装する

1. 最新mainを取り込んだ後に公開候補を生成する
2. release-manifestを作り、品質監査記録へハッシュを記載する
3. Claude独立レビューを受ける
4. 指摘反映後のコミットSHAとmanifestをCEOが承認する
5. 承認後は再生成せず、同じ成果物を一本化した公開元へ反映する
6. 本番とmanifestを照合し、結果を引き継ぎ台帳へ残す

**成功の形**: 「承認したものと少し違うものが公開された」が機械的に起こらない。

### 段階5: 旧経路を停止する

1. HTMLから件数を抽出する暫定処理を削除する
2. 未使用の固定件数ファイル、重複サイトマップ生成、全テーマ一括書換えスクリプトを停止する
3. 旧ルートリポジトリから数字を除き、案内・転送だけにする
4. 非公開正典のバックアップから、別worktreeで完全監査を再現する

削除は、参照0件、復元方法、CEO承認を確認してから行う。

## 7. データベース方式の判断

| 案 | 判断 | 理由 |
|---|---|---|
| 既存 `reaction_map.sqlite3` を正典化 | 不採用 | 2事例だけで現行10テーマと不一致。バイナリ差分をレビューしにくく、投稿本文等を含む |
| 新しいSupabase/PostgreSQLを正典化 | 今回は保留 | 複数人の同時編集、API、リアルタイム更新が必要になってから検討する |
| Git管理JSONを公開正典にする | **採用** | 変更差分、承認時点、巻き戻し、静的サイト生成との相性が良い |
| JSONからSQLiteを毎回生成 | 補助として採用可 | 集計調査は速くなるが、消して再作成できる派生物に限定できる |

将来、更新頻度や担当者が増えて外部DBが必要になった場合も、公開データ契約とrelease-manifestは維持する。
保存先を変えても、公開前の固定・レビュー・承認を省略しない。
