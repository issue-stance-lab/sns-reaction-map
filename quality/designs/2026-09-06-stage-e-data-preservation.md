# 段階E：Xデータの保全と継続運用

## 保存境界

Xデータ関連の範囲を、投稿本文を持つ `social-samples/` 全456ファイル、非公開ペルソナ1ファイル、段階Dが現に参照する外付けの採否根拠7ファイルに固定した。資産台帳 `company/data-assets.json` に保存先・相対パス・指紋・サイズを記録する。投稿本文・生ID・投稿URLは台帳に含めない。会社全体のアカウント、契約、制作媒体の全資産まで棚卸し済みという意味ではない（課題50の別工程）。

| 区分 | 保存先 | 初回対象 |
|---|---|---:|
| Git追跡中のXデータ | Git履歴 | 303ファイル、うち正典4テーマ |
| Git管理外のXデータ | 非公開原本アーカイブ | 153ファイル、うち正典7テーマ |
| 非公開ペルソナ | 同じ非公開原本アーカイブ | 1ファイル |
| 採否の元資料 | 採否根拠アーカイブ | 7ファイル |
| 分類基準、生成器、再読・採用台帳、検証データ | Git履歴 | 復元に用いたcommitを記録 |

Git追跡中の本文付きファイルは以前からの状態を記録したもの。今回Gitへ新たに本文を追加していない。保存境界を記録することと、本文の公開可否を承認することは別。元ファイルの移動・削除、Git履歴の書き換えは行わない。

`social-samples/` にGit追跡もignoreもされていない新規ファイルがあれば台帳作成を止める。追跡資産の未コミット変更、必須原本の欠落、採否根拠の指紋不一致でも止める。単にファイル名の日付が古いという理由で削除しない。過去の実験・分類版も保管対象には含むが、そのまま採用対象とはしない。

段階Dの「本文付き原本が今回の照合元に無い4保存回」は引き続き未確認。保全処理で本文を新たに復元したとは言わない。

## 保全先・世代・復元記録

正規保存先は既存の `/Volumes/HD-LE-B/issue-stance-private-backups`。課題33で決めた個人運用・非暗号化・全世代保持を維持する。新しい有料サービスや保存先は導入しない。自動削除は実装しない。

- 原本：`private-data-*.tar.gz`。作成・展開検査後に `company/data-backup-status.json` を更新。
- 採否根拠：`adoption-evidence-*.tar.gz`。段階Dの参照和集合を指紋照合して保存し、同じ復元検査を通して `company/data-evidence-backup-status.json` を更新。
- 再生成実験：`company/data-restore-status.json`。Gitの新しいクローンと2つのアーカイブだけから復元し、正典からの公開JSON・11テーマの生成器・再読台帳・採用台帳を検査した記録。

成功記録はアーカイブ名・指紋・件数・日時・Git版を持ち、原文と保存先の絶対パスは持たない。バックアップや検査が失敗したときに前回の成功日時を進めない。前回の記録は残り、管理画面に7日超を表示する。

復元検査はファイルの欠落・重複・余分なファイル・サイズ・指紋・JSON件数の不一致を拒否する。パスの外部への脱出、リンク、重複JSONキーも拒否する。旧アーカイブはこの範囲で互換性を維持する。

**記録は最終検査時点の証拠**。外付けディスクの現在の接続や故障を常時監視してはいない。再生成実験を再実行すると実アーカイブの指紋と復元内容まで確認できる。物理的な別マシンでの試験は未実施で、課題33・50に残す。

## データ更新のたびに行うこと

隔離作業ツリーでデータと段階C・Dの台帳を更新してから、次を実行する。

```sh
python3 scripts/backup_private_data.py --dest /Volumes/HD-LE-B/issue-stance-private-backups
python3 scripts/backup_adoption_evidence.py --dest /Volumes/HD-LE-B/issue-stance-private-backups
python3 scripts/data_asset_inventory.py
python3 scripts/verify_data_assets.py
python3 scripts/data_asset_inventory.py --check
```

成功時は復元確認OK、保全状態がprivate・externalともverified、保存境界検査OKとなる。更新した本文なしの成功記録と資産台帳を同じ作業ブランチへコミットする。Git資産自身の未コミット変更がある場合は、先にその変更をコミットする。

別の場所へ採否根拠を復元した環境では、採否根拠の保存・資産台帳・段階Dの生成器に `--evidence-root <復元先>` を渡す。保存先のハードディスク名を再現する必要はない。

## Git＋アーカイブだけで再生成できるかを確かめる

対象コード・成功記録・資産台帳をコミット後、同じ作業ツリーで実行する。

```sh
python3 scripts/verify_data_asset_restore.py --backup-root /Volumes/HD-LE-B/issue-stance-private-backups
```

成功時は復元後の6検査がOKとなり、最後に「Git＋原本＋採否根拠からの復元・再生成（同じマシン）」が表示される。新しい一時フォルダへGitをクローンし、原本154ファイルと採否根拠7ファイルを復元する。元の作業ツリーから無視ファイルをコピーして補わない。公開JSON10テーマは原本から完全一致、全11テーマの生成器は再実行可能性を検査する。新しい実機を使った証拠にはしない。

この成功記録もコミットする。記録には試験したコードのcommitと資産内容の指紋を残すため、記録自身をコミットした後のcommitと同じでなくてもよい。

## 管理画面と担当・期限

`python3 scripts/build_admin_dashboard.py` でローカル画面を生成する。成功時に出力先が表示され、「データ資産の品質と保全」に採用状態、再読、保管境界、復元記録、担当と期限が出る。原文は出さない。7日超の記録、検査失敗、未管理、期限超過を正常や0件に読み替えない。

運用の正典は `company/data-operations.yaml`。週1回の保全確認、採否判断の計画、未読差分、別実機復元を登録した。期限は今回の計画で、過去の実施や承認を表すものではない。更新があったときの保全は週1回を待たず実行する。確認担当が実施後に次回期限を更新する。

段階Eの完成は保全・検査・管理の共通基盤がつながった意味。正典外525件の採否、未読差分、課題59の汎用統合、課題54の新ページ展開は残る。
