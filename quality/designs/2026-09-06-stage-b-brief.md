# 課題63 段階B: 入口を整える（別セッション用の指示文）

この1枚だけで作業できる。**他の文書を読む必要はない。**

## 最初に読むこと（急ぎの発見）

**分類モデルの設定が、運用文書と食い違っている。次の収集を回す前に決着させること。**

| | いま |
|---|---|
| `DATA_REFRESH.md` の記述 | 分類モデルは **`kimi-k2.6`** |
| `~/.hermes/config.yaml` の実設定 | **`upstage/solar-pro4:free`**（2026-09-06 08:18 に更新されていた） |

`DATA_REFRESH.md` 自身が、モデルを替えると**賛否の構成比が最大4ポイント動く**と記録している
（2026-08-18の実測。同一30件で `kimi-k2.6` との一致率は論点77%・賛否73%）。
**このまま次の収集を回すと、正典に別モデルの分類が黙って混ざる。**

しかも**どの回をどのモデルで分類したかは、どこにも記録されていない。**
だから混ざっても後から分からない。**これを可能にしているのが段階Bの穴そのもの。**

### 最初にやること

1. **オーナーに確認する。**「`kimi-k2.6` に戻すのか、`upstage/solar-pro4:free` を正とするのか」。
   これは運用方針の変更なので、勝手に決めない
2. 決まったほうへ**設定と文書の両方をそろえる**
3. **`pgrep -fl "classify_.*hermes|refresh_topic"`** で他セッションが分類中でないことを確認してから設定を触る
   （設定を変えた瞬間に他セッションも切り替わり、1回の更新でモデルが混ざる）

### 収集回ごと：足りないものがある

`social-samples/updates/{日付}/report.json` に、回ごとの記録がすでにある。

```
checks / raw / duplicates / new / relevant / opinions / opinion_flag_available /
candidate / classification_errors / status / topic / date / run_id /
queries / taxonomy / timings / next_collect_at
```

**入っていないもの（段階Bで足す）**

| 足すもの | なぜ要るか |
|---|---|
| **分類モデル名** | いちばん上の問題。どの回をどのモデルで分類したか分からない |
| **プロンプト・分類基準の版** | 基準を変えたのか、モデルが変わったのか、世論が動いたのかを区別できない |
| **入力の指紋（生データのsha256）** | 同じ入力から同じ結果が出るかを後で確かめられる |
| **取得元** | 投稿ごとには入っているが、回の単位では残っていない |

## やること

1. **`report.json` に上の4つを足す。**書き手は `scripts/refresh_topic.py`
2. **新しい回でこれらが欠けていたら止める検査を作る。**
   `scripts/` に検査を1本足し、`tests/` にその検査のテストを足す
3. **投稿ごとの必須項目（取得日時・検索語・取得元）が欠けたら止める検査も足す。**
   自転車の116件は「欠けたまま通ってしまった」から生まれた
4. **過去の回は対象外にする。**古い `report.json` には新しい項目が無い。
   さかのぼって埋めない（推測値を記録に混ぜない）。**いつの回から必須になるかを検査に書く**

## 完了の確かめ方

```bash
python3 -m unittest discover -s tests
python3 scripts/verify_theme_page.py
python3 scripts/verify_number_provenance.py
python3 scripts/verify_top_page.py
```

成功の形: `OK` と `NG 0件`。

**そのうえで、実際に止まることを確かめる。**新しい項目を1つ抜いた `report.json` を
作って検査に掛け、**止まること**を確認する。止まらなければ検査になっていない。

## やってはいけないこと

- **オーナーに聞かずにモデル設定を変えない。**どちらを正とするかは運用方針の変更
- **他セッションが分類中に設定を触らない。**1回の更新の中でモデルが混ざる
- **過去の回に推測でモデル名を埋めない。**「不明」は不明のまま残す。
  課題63の学びは「分からないものを一律に埋めない」こと
- **検査を作らずに文書だけ直さない。**このプロジェクトは
  「指示文の禁止事項は別セッションで破られる。検査だけが残る」を何度も経験している
- **共有ツリーで作業しない。**`git worktree add ../isa-wt-<名前> -b task/<名前> main`
