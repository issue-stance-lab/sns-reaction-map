# 課題84: 公開済みページの構造(ヒートマップCanvas・漫画/投票画像)を定期的に再監査する仕組みが無い

**状態**: 完了。`scripts/verify_page_structure.py` を新設し `run_public_checks.py`(CI)に接続した(2026-09-21)

## 経緯

2026-09-21、オーナー依頼「課題管理の棚卸し・旧課題管理で行っていないものの抽出」で発見。

廃止前の `LOOP.md`「① 監査」は、**毎回のループで**次を確認していた(2026-08-23廃止時点の全文、
`git show d3359d0c^:LOOP.md` で復元可能)。

- HTMLに `smCanvasMain` / `smCanvasHeat`(ヒートマップの土台となるcanvas要素)が存在するか
- `docs/images/` に漫画・投票画像が存在するか
- 2D分類JSONの件数とエラー率
- `sitemap.xml` への掲載有無
- `collect_at` / `refresh_at` の超過

廃止時のコミット(`d3359d0c`)で、更新チェックリストは `DATA_REFRESH.md` へ、
`collect_at`/`refresh_at` 超過検知は `build_admin_dashboard.py` へ、それぞれ引き継がれたことを
コミットメッセージで確認できる。しかし**「①監査」の残り3項目(smCanvas存在・画像存在・
分類JSONエラー率)を引き継いだ先が見当たらない**。

現在の検査を確認した結果:

- `scripts/verify_theme_page.py` は数値の整合性(分母・件数の突合・最大論点バッジ等)が対象で、
  `smCanvasMain` / `smCanvasHeat` は扱っていない
- `smCanvas` という文字列が出るのは `build_bukatsu_arena.py` 等の**ページ生成スクリプト側**のみ。
  生成時に書き込む処理はあっても、**公開済みHTMLに実際に残っているかを事後チェックする処理は無い**
  (`scripts/` `tests/` を横断検索して確認済み)
- 漫画・投票画像の存在チェックも同様に見当たらない
- 2D分類JSONのエラー率を継続的に見ている検査も見当たらない

## なぜ実害の可能性があるか

この種の「後から静かに壊れる」パターンは実際に2回起きている。

1. 2026-09-13: 共有コード(生成器)を直しても本番HTMLには自動反映されないため、
   修正済みのはずの不具合が5テーマで反映漏れのまま残っていた(`feedback_shared_fix_needs_republish` 系)
2. 2026-09-21(課題80): 山なみ区間の共通再生成処理で、副首都ページの論点画像7枚が本番から
   消えていたことが**別作業の副産物で偶然発覚**した。課題80の対応範囲は原因となった
   共通経路の特定・修正であり、「次に同種の脱落が起きたときに検知する仕組み」までは含まれていない

つまり、個々の事故は都度直しているが、**旧LOOP.mdが毎回やっていた「壊れていないかの
定期的な再確認」に相当する仕組みが今は無く**、次に同じ種類の脱落が起きても、
人間かAIが該当ページを開いて偶然気づくまで検知されない。

## 対応方針 → 実装内容(2026-09-21)

オーナー承認により(a)(CIに乗せる)で実装。実装前に現行ページの実物を確認したところ、
**smCanvasMain/smCanvasHeatをそのまま検査するのは誤りだった。**「議論の山なみ」
リニューアル(課題54)でチャート実装がcanvasからSVG＋インラインJSON
(`window.PLANET_DATA`)へ変わっており、これらのIDは現在CSSにセレクタが残るだけの
死んだ指定(実体の無いスタイル定義)になっていた。旧チェックリストの文言をそのまま
実装せず、実物に合わせて書き直した。

`scripts/verify_page_structure.py` を新設し、次を確認する(`run_public_checks.py`経由でCI接続):

1. **チャートに実データが入っているか**: ページごとに技術を自動判定し、
   `window.PLANET_DATA`(10テーマ)ならstances/modesが空でないこと、
   `<canvas>`(takaichiの旧アリーナ形式)ならデータ用scriptファイルが存在し空でないことを見る
2. **画像・スクリプトの参照切れ**: `<img src>` / `data-img` のローカル参照が実在するか
3. **JSが組み立てる論点画像パス**: `topic-modern.js` 共通コード側で画像パスをJS文字列結合
   で作る7テーマについて、`{論点id: slug}` の対応表から実際のファイルを逆算して確認する
   (課題80で実際に消えたのはこの種類の画像)

実装中に見つけた副次的な問題: `src="…"` を素朴に正規表現で探すと、`<script>`内のJSコードが
組み立てる文字列(`'+aicImgPath+'` のような結合の断片)まで拾ってしまい、42件の誤検知が出た。
`<script>...</script>` の中身(タグ自体は残す)を空白に置き換えてから探すことで解消した。

**意図的に対象外にしたこと**: ディスク上にあってページから参照されていない画像の検出。
`xxx-bousai.webp` と `xxx-bousai-v2.webp` のように差し替え後の旧バージョンが正当に
残っていることが多く、単純な「参照されていない」だけでは誤検知になる。

**動作確認**: 実際に画像ファイル・データファイルを一時的にどかしてNGになること、
JSON側を壊してNGになることを確認したうえで復元(3パターンとも正しく検知)。
`tests/test_page_structure.py` にも同じ観点のテストを固定した(11件、実データ1件＋合成データ10件)。

## 影響範囲

新規スクリプトとテストの追加、`run_public_checks.py` への1行登録のみ。
既存の公開ページ・他の検査は変更していない。CIには公開ファイルのみの検査として乗る
(非公開正典は読まない)。
